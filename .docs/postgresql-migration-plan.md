# Plan: migrate `db.json` to PostgreSQL

Status: **complete. All decisions are made and all seven phases (Docker Postgres 18, schema and migrations, Express API, `db.json` import, frontend cutover, API tests, cleanup) are done and verified. See "Follow-ups" for what is left outside this migration.**

## What we found

- **Data:** one collection, `users`, with 14 records at the time of the import (10 when this plan was first written). Every record has the same six fields: `id`, `firstName`, `lastName`, `nickname`, `email` and `currentActivity`. There are no duplicate emails or missing values, and the longest value is 29 characters.
- **Frontend contract:** `src/app/users/services/users.service.ts` calls `http://localhost:3000/users` with `GET`, `POST`, `PUT /:id` and `DELETE /:id`. Ids are numbers.
- **The create form sends `id: ''`** in the POST body, and the server must ignore it.
- **Missing piece:** PostgreSQL doesn't serve REST on its own. `json-server` is currently the API, so we need a small backend service between Angular and the database.
- **Local environment:**
  - **Postgres 14:** it's already running on port 5432 (Homebrew), and Docker is installed. PostgreSQL 14 reaches end of life in November 2026, so a newer version is recommended for this project.
  - **`.gitignore`:** it has no `.env` entry yet, which has to be added before any credentials exist.
  - **`.vscode/db-local.json`:** this file exists and has not been opened. Check it for credentials before wiring anything.

## Target design

```
Angular app  ->  Express API (server/, TypeScript)  ->  Drizzle  ->  PostgreSQL (Docker Compose)
 (unchanged)      same contract as json-server
```

**Stack:**
- **API:** Node.js with Express and TypeScript, in a separate `server/` project.
- **Database access:** Drizzle ORM, with the schema written in TypeScript and migrations generated by `drizzle-kit`.
- **Database:** a current PostgreSQL major version (17 or newer), run through Docker Compose.
- **Versions:** confirm the current versions of Express, Drizzle, `drizzle-kit`, the Postgres driver and Postgres itself at install time, rather than relying on this plan.

**Initial schema:** one table, `users`, matching today's data shape.

| Column | Type | Notes |
|---|---|---|
| `id` | integer, `GENERATED ALWAYS AS IDENTITY` | Keeps numeric ids, so no frontend change. Clients can't set ids, so the Phase 4 import must use `OVERRIDING SYSTEM VALUE`. |
| `first_name`, `last_name` | text, not null | CHECK: trimmed length 2–100, matching the form rules. |
| `nickname`, `current_activity` | text, **nullable**, no default | Blank values are stored as `NULL`. The API converts blank input to `NULL` on write and returns `''` on read, so the Angular `User` type doesn't change. CHECK on non-null values: trimmed length 1–100 (nickname) and 1–200 (activity), so an empty string is rejected and the API **must** send `NULL`. |
| `email` | `citext`, not null, **unique** | Case-insensitive uniqueness (`users_email_unique`). CHECK: length 3–254. |
| `created_at`, `updated_at` | timestamptz, not null, default `now()` | A trigger sets `updated_at` on every UPDATE, even if a client supplies a value. |

The API and frontend keep camelCase, while the database uses snake_case, with a mapping in the API layer.

**Ready for auth, but nothing built yet:** `users` stays the identity table, because email will become the login. Later migrations would add `roles`, `permissions`, `user_roles`, `role_permissions`, a separate `credentials` table (password hashes) and `sessions`. Those would be many-to-many join tables with foreign keys to `users`, and none of them need to change `users`.

## Phases

Each phase ends with a check and a pause for review, as in the Angular migration.

**Phase 0: decisions.** Done (see the end of this doc).

**Phase 1: provision the database.**
- A `docker-compose.yml` with a pinned Postgres major version (17 or newer), a named volume and a health check. It would use a non-default host port (5433) so it can't collide with the existing Postgres 14 on 5432.
- A dedicated `nglab` database and a least-privilege app role, never the superuser.
- `.env` (gitignored) plus a committed `.env.example`, and a `.env` entry added to `.gitignore`.

**Phase 2: schema and migrations. Done.**
- `server/` is a separate ESM project (own `package.json`, lockfile and `tsconfig.json`), with pinned `drizzle-orm` 0.45.4, `drizzle-kit` 0.31.11, `pg` 8.23.1 and TypeScript 5.9.3.
- The `users` table is defined in `server/src/db/schema.ts`, and three migrations are committed in `server/drizzle/`: `enable_citext` (hand-written), `create_users` (generated, including the identity column, unique constraint and CHECKs) and `users_updated_at_trigger` (hand-written).
- `citext` is a custom column type in the Drizzle schema. `drizzle-kit` generated everything except the extension and the trigger.
- Scripts: `npm run db:migrate` and `npm run db:generate` at the repo root proxy to `server/`. Migrations run as `nglab_admin` (`MIGRATION_DATABASE_URL`), and the API will connect as `nglab_app` (`DATABASE_URL`).
- Verified against the Docker database as the app role: constraints, the trigger, SELECT/INSERT/UPDATE/DELETE all work, DDL and TRUNCATE are denied, and a second migrate run applies nothing.
- **Known audit note:** `npm audit` reports 4 moderate findings in `server/`, all from `drizzle-kit`'s dev-only `@esbuild-kit` chain (an old esbuild dev-server advisory). The suggested fix downgrades `drizzle-kit`, so it was left alone. Revisit when moving to Drizzle 1.0.

**Phase 3: the Express API (replaces `json-server`). Done.** It keeps the exact contract:

| Request | Behavior |
|---|---|
| `GET /users` | Ordered by `id`. json-server returned insertion order, and SQL needs an explicit sort. |
| `POST /users` | Ignores the incoming `id` and returns the created row with its real id. |
| `PUT /users/:id` | The path id wins, and it returns the updated row. |
| `DELETE /users/:id` | Returns `{}`, or 404 if the id doesn't exist. |

- **Safety:** Zod validates every field (the same rules as the database CHECKs, accepting the form's `id: ''` and `null` optional fields), queries are parameterized (Drizzle), and CORS is restricted to `http://localhost:4200` instead of allowing any origin. That addresses the earlier review findings about weak input validation and the open CORS setting. The body limit is 10 KB.
- **Structure:** routes, a thin users repository on top of Drizzle, and one central error-handling middleware that maps errors to 400 (validation, bad id, bad JSON), 404, 409 (duplicate email), 413 and 500. Blank optional fields are stored as `NULL` and returned as `''`.
- **Operations:** a `/health` endpoint that checks the database, graceful shutdown, and request logging with only method, path (no query string) and status. Error logs never include the raw error, because Drizzle's wrapper message embeds the query parameters (user data).
- **Port and run:** port 3000 on `127.0.0.1` (override with `PORT`, `HOST`, `CORS_ORIGIN`, `LOG_LEVEL`). Start it with `npm run api`.
- **Bruno collection:** `server/bruno/` holds a collection in the `.bru` format (it works in every Bruno version). Open that folder in Bruno and select the `local` environment (`baseUrl` is `http://localhost:3000`). It has 10 requests covering health, list, create, duplicate email (409), invalid body (400), update, unknown and invalid ids (404 and 400), and delete (200 and then 404). It creates its own user with a unique email, updates and deletes it, and never touches existing users, so it is safe to run repeatedly. To run it from the terminal without installing anything: `cd server/bruno && npx @usebruno/cli run --env local` (the API must be running).

**Phase 4: import `db.json`. Done.** `npm run db:seed` (add `-- --dry-run` or `-- --upsert`; the options go after the `--`):
1. Validates the whole file first and lists every problem (invalid fields, duplicate ids, case-insensitive duplicate emails), with a `--dry-run` mode that also reports what would change.
2. Inserts all rows in one transaction, **preserving the existing ids** (`OVERRIDING SYSTEM VALUE`, written as a parameterized raw insert because Drizzle 0.45 has no public API for it). It runs as the admin role.
3. Resets the id sequence to `max(id)`, so the next created user doesn't collide.
4. Verifies by reading the table back and comparing it to the file row by row, plus checking the sequence.

- **Safe to re-run:** it refuses a non-empty table unless `--upsert` is given. `--upsert` updates rows with matching ids, inserts the rest and leaves other rows alone, so re-running on identical data changes nothing.
- **Verified:** after the import, the API's `GET /users` output was identical to the committed `db.json`. A failed import (for example an email clash) rolls back completely and prints a short message.

`db.json` was rewritten whenever the app was used against `json-server`, so the committed version is the canonical seed. It now holds **14** users (the plan originally counted 10), all valid. It stays in the repo as the seed fixture.

**Phase 5: frontend cutover. Done.**
- **Change:** the API URL moved out of `users.service.ts` into environment files generated with `ng generate environments` (`src/environments/environment.ts` and `environment.development.ts`, each with `apiUrl`, plus a development `fileReplacements` entry in `angular.json`). The contract was identical, so nothing else changed. The production file still points at `http://localhost:3000` because there is no deployed API yet; set it before building for a real host.
- **Verified in the browser** against Express and Postgres (using a test user, with the 14 seed users untouched): the list loads from the database, creating a user (blank optional fields) works and the database assigns the id, editing works including a direct visit to `/users/manage/:id` after a full page load, a duplicate email with different case is rejected (409) and shows the store's generic error notice, and deleting shows the confirmation prompt and highlighted row, removing the row only after confirming. The 54 unit tests and both build configurations pass.
- **Ids have gaps:** the identity sequence advances even for rejected inserts (such as the 409 above), so ids are unique but not contiguous.

**Phase 6: tests. Done.** Run them with `npm run api:test` (starts the test database, then runs Vitest in `server/`).
- **Throwaway database:** a second Compose service, `db-test`, behind the `test` profile so `npm run db:up` never starts it. It uses the same image and init script as the real database (so the roles and privileges match), keeps its data in memory (`tmpfs`) and runs with `fsync` off. It listens on `127.0.0.1:5434` (`TEST_DB_PORT`). Start and remove it with `npm run db:test:up` and `npm run db:test:down`. Testcontainers was not needed.
- **Runner:** Vitest (pinned, dev-only; it adds no new audit findings), with Node's built-in `fetch` instead of supertest. Files run serially because they share one database. Global setup applies the real committed migrations, so the migration files are tested too.
- **Safety:** the tests truncate tables, so they derive their connection from your dev credentials but force `TEST_DB_PORT`, refuse any non-local host, and refuse to run if `TEST_DB_PORT` equals the development database's port.
- **What is covered (84 tests):**
  - API (`users.api.test.ts`): every endpoint, validation (10 invalid-body cases), duplicate emails (409, case-insensitive, on create and update), id handling (path id wins, body id ignored, invalid ids), 404s, malformed JSON and oversize bodies, CORS, health, and logs that contain no user data, including a forced database failure (Drizzle's error message embeds the query parameters).
  - Database (`db.constraints.test.ts`), as the app role: identity ids, the unique email, every CHECK, NOT NULL, the `updated_at` trigger and the app role's privileges (DDL and `TRUNCATE` denied).
  - Import (`seed.test.ts`): the seed validation, and the real `db:seed` script run against the test database (id preservation, sequence reset, `--dry-run`, `--upsert`, rollback).
- **The tests can fail:** I temporarily broke four behaviors (the 409 mapping, logging the raw error, blank-to-`NULL`, and the sequence reset) and each was caught by the expected tests.
- The existing Angular tests (54 at the time of writing) are unchanged.

**Phase 7: cleanup and docs. Done.**
- `json-server` and the `backend` npm script are removed (35 packages left the lockfile, with no version changes), replaced by the `db:up`, `db:migrate`, `db:seed`, `api` and `api:test` scripts. `db.json` stays in the repo as the seed fixture only.
- **Audit:** removing `json-server` did not change the root `npm audit` total (31 findings: 3 critical, 7 high, 21 moderate, before and after). The earlier expectation that it would clear the `morgan` and `path-to-regexp` findings was out of date. The remaining findings come from the Angular toolchain (`@angular/build`, `@angular/cli`, `vite`, `undici`, and the MCP SDK and its dependencies that the CLI bundles), so they need an Angular or CLI update rather than a change here. `server/` has 0 runtime findings and the 4 known dev-only `drizzle-kit` findings.
- The README now has setup steps and a command table, and `.github/copilot-instructions.md` describes the Express and Postgres backend instead of `json-server`.

## Behavior changes to expect

- **Duplicate emails:** creating a user with an email that already exists is rejected with a 409. The Angular store now shows a generic error notice ("Unable to add the user. Please try again."), so the user sees a failure but not the reason. A specific "email already exists" message is a small follow-up.
- **Validation:** the server now enforces the rules (lengths, email format), not just the form.
- **Stricter ids:** non-numeric ids return 400 or 404 instead of being passed through.

## Decisions

**Made:**
1. **Backend framework:** **Express with TypeScript**, in a separate `server/` project. (The earlier NestJS suggestion is dropped.)
2. **Database access:** **Drizzle**, with `drizzle-kit` for migrations.
3. **Where Postgres runs:** **Docker Compose with a current Postgres (17 or newer)**. The local Postgres 14 isn't used.

4. **Primary key:** **integer identity**, so the Angular app needs no changes.
5. **Blank nickname or activity:** **store `NULL`**. The API maps blanks to `NULL` on write and `NULL` to `''` on read, so the frontend contract is unchanged. The `db.json` import converts `''` to `NULL`.
6. **Email uniqueness:** **enforced, case-insensitive** (`citext`). Duplicates get a 409.
7. **Deletes:** **hard delete**, as today. Soft delete or an audit trail is a later decision, once users own auth data.
